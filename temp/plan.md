## 1. 技术选型（本轮定，第三轮不再改）

选定：TypeScript + React + Vite，纯前端，无后端。

理由（对着“完美复刻”这个目标）：
- 复刻的本质是数值与规则精确，不是实时渲染。规则内核写成纯 TS 函数即可被单元测试逐条钉死。
- 界面必须和 `场地.docx` 一致，React 组件适合像素级摆版，改样式不动逻辑。
- 数据驱动：角色/道具/技能全部落成 JSON 表，docx 只作为取值来源，改数值不改代码。
- 备选与环境记录：Godot 适合真游戏但 UI 排版弱、数值迭代慢；Python 桌面分发与界面都不占优；Unity 过重。故排除。

分层（三层，禁止跨层）：
- `core/` 规则内核：纯函数，无 DOM、无 React、无 IO。输入状态 → 输出状态 + 事件日志。
- `data/` 数据表：角色、道具、技能、场地、BP 池，JSON。
- `ui/` 表现层：只读事件日志渲染，不写规则。

## 2. 大步骤（P0–P6，串行，每步有验收断言）

P0 素材抽取（只做一次，产物沉淀在 temp/）
- 输入：上级目录 5 份 docx（机制由我本人读，其余交子智能体）。
- 产出：`temp/extract/` 每份一份结构化摘要 md；`temp/data/` 可直接吃进内核的初版 JSON。
- 验收：机制文档里每条规则都能在 JSON 里找到落点，或明确标注“未实现”。

P1 规则内核 MVP
- 内容：实体（角色/单位）、资源（血量等）、回合、行动、结算顺序、胜负判定。
- 产出：`core/` + 单测，测试名直接引用机制文档条款编号。
- 验收：`pnpm test` 全绿，且每个机制条款至少一条测试。

P2 单场闭环（无界面）
- 内容：CLI 跑一场完整对局，逐步打印事件日志。
- 验收：一场对局能从头走到分出胜负，日志数值与手工推算一致（断言脚本）。

P3 界面复刻
- 内容：先静态还原 `场地.docx` 的版面与元素，再接内核事件流。
- 验收：截图与文档示意图逐区对照，元素齐全、位置关系一致。

P4 BP 流程
- 内容：按 `普通对局BP流程` 实现选/禁顺序与状态机，接到 P3 的进场。
- 验收：BP 全流程可走通，非法操作被拦截。

P5 角色与道具全量
- 内容：按 `角色.docx`、`道具.docx` 填满数据表，逐个技能接内核钩子。
- 验收：每个角色/道具都有一条可跑的用例，无“空实现”残留。

P6 细节对齐与回归
- 内容：按 `Q&A.docx` 逐条核对边界情况；建立 golden 快照回归。
- 验收：Q&A 每问有对应测试或明确的“文档未定义，按 X 处理”记录。

## 3. 每轮对话的工作方式

## 5. 第三轮：最终目标与详细方向

### 5.1 最终目标（验收定义）
规则与内容 100% 与文档一致，可在桌面浏览器完整打完一局；界面可用、信息齐全，不追求像素级还原。
可判定标准：
- `pnpm test` 全绿，机制文档每条规则有对应测试；
- 一场完整对局的日志数值与手工推算一致；
- 每个角色/道具/技能都有可跑用例，无空实现；
- `Q&A.docx` 每问要么有测试，要么有“文档未定义，按 X 处理”的记录。

### 5.2 目录职责（硬边界）
- `core/`：状态机与结算，纯函数，输入 State → 输出 {State, Events}。禁止 import react、禁止访问 DOM、禁止读文件。
- `data/`：JSON，数值唯一来源，代码中不出现魔法数字。
- `ui/`：只消费 Events 渲染，不写规则判断。
- `scripts/`：构建、断言校验、文档抽取。
- `test/`：单测与 golden 快照。

### 5.3 针对“不熟悉前端”的应对
- 启动一条命令，后期补双击即跑的 `start.cmd`。
- 你日常要看/要改的只有 `core/` 和 `data/`，二者写成普通脚本样式：无装饰器、无异步、无框架 API。
- `ui/` 一次性投入，我维护，你按截图验收。
- 每阶段交付附三段说明：怎么跑、改哪个文件能改数值、怎么判断改对了。

### 5.4 执行顺序与交付物
P0 抽取：`temp/extract/*.md` + `temp/data/*.json`（初版）+ 规则条款清单。
P1 内核：`core/` + `test/`，条款与测试一一对应。
P2 闭环：`scripts/play.ts` 跑完整对局，输出可断言的事件日志。
P3 界面：`ui/`，静态版面 → 接事件流。
P4 BP：`core/bp.ts` + 界面接入。
P5 数据全量：`data/` 填满，逐条用例。
P6 对齐：golden 快照 + Q&A 核对表。

### 5.5 风险与预案
- 文档歧义：记入 `temp/open-questions.md`，不猜，先问。
- 数值散落：一律进 `data/`，校验脚本断言“代码中无裸数字”。
- 你无法读前端代码：关键判断全在 `core/`，`ui/` 出错表现为显示问题而非规则问题。

## 6. P4 最终方案（第 3 版，2026-11-06，不再变更）

### 6.1 数据
- `data/characters.json` 逐条新增 `cost`（千为单位折算成整数，1k=1000），来自 `temp/extract/角色.md` 的「花费：Nk」，共 43 条；脚本 `temp/extract-cost.mjs` 一次性写入并打印映射表，断言 43/43 命中、范围 1000–5000。
- `core/types.ts` 的 `CharacterDef` 增 `cost: number | null`。

### 6.2 `core/bp.ts`（纯函数，无框架）
- 变体：`single`（一局一胜 2/2/false/false）、`bo3`（BO1 2/2/true/true、BO2 2/1/true/true、BO3 1/1/false/false）、`bo5`（BO1 2/2/true/true、BO2 2/1/true/true、BO3 1/1/true/true、BO4、5 1/1/false/false）。
- 8 步骨架：`ban(b1) → ban(b1) → pick 2 → pick 2 → ban(b2) → ban(b2) → pick ≤3 → pick ≤3`；actor 为先手/后手交替（先手先动）。
- 先手方：第 1 小局 `p1`，之后逐小局轮换（奇数局 p1、偶数局 p2），见 Q34。
- 校验：可用性（对方本局 BAN 名 ∪ 自己全局 BAN 名 ∪ 已选同名上限）、预算 14k（每小局重置，QA-01）、人数（首轮固定 2 + 次轮 0–3，Q35≡Q19）、稀有度（同名限定/史诗 ≤1、同名普通 ≤2、限定人头 ≤2 且不同名、史诗不限，Q20/Q37）。
- BAN：按角色名连坐，只作用于对方；已选出的角色不受后续 BAN 影响（Q37）。同一小局内同一名字不允许被重复 BAN（冗余操作直接拒绝，记入待确认）。
- 全局 BAN：仅 `entersGlobalBan` 步的 pick 进入该玩家私有集合，跨小局累积、不可解除，系列赛结束清空（Q36）。
- 系列赛：`createSeries/recordRoundWinner/advanceSeries`，按 `seriesWinsNeeded`（1/2/3）判冠军。
- 费用折算：`toItemBudget(leftover) = leftover × 2`（Q12/Q21），由 `createGame` 的可选参数接收。

### 6.3 界面（`ui/app.js`，无 JSX、走 AMD）
- 首屏：赛制选择（一局一胜/三局两胜/五局三胜）→ 进入 BP。
- BP 面板：双栏（先手方 / 后手方），每栏显示玩家名、剩余预算条、限定计数、人数、第一次/第二次 BAN、已选角色、全局 BAN；顶部显示当前步骤与行动方。
- 角色网格：只有 `legalBpChoices()` 返回的角色可点，其余置灰并给 `title` 原因；「结束本轮选择」仅 atMost 步出现。
- BP 结束：站位排序（↑/↓ 交换）→「开始对局」，按排序结果建单位，先手方 = 本局 BP 先手方。
- 对局结束：记录小局胜者；未出冠军则「进入下一小局」重开 BP（携带全局 BAN、换先手），出冠军则显示系列赛结果。

### 6.4 测试与验收
- `test/bp.test.mjs`：数据 cost 完整性、7 变体参数、8 步流程、预算、稀有度/同名、全局 BAN 私有与跨局、BO3 可同选、先手轮换、冠军判定、折算公式。
- `scripts/check-ui.mjs`：改为断言 BP 首屏、BP 面板、按内核动作走完整个 BP 后渲染对局页、以及既有对局断言。
- 硬验收：`npm run verify` 全绿。
- 收尾：写 `temp/handoff-P5.md`。
